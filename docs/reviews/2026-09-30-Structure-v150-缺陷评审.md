## P1 — 确定的功能性缺陷

### P1-1【最值得修】`ComputeCisdFvgFollow` 的 `weak` 只置真、从不复位 —— 强 CISD/OB 被永久标弱

**位置**：`Indictor/TradFi_Structure.mq5:3660-3678`

```mql5
      bool found = false;
      for(int v = 0; v < g_result.nFVG; v++)
      {
         if(g_result.fvg[v].dir != dir) continue;              // 必须**同向**
         int fb = g_result.fvg[v].bar;                         // FVG 的确认 bar（c3）
         if(fb <= b && fb >= b - InpCisdFvgLookahead) { found = true; break; }
      }
      if(found) continue;

      // 后续窗口内没有同向缺口 → 该次 CISD 判为弱
      g_result.cisd[k].weak = true;
```

**为什么错**：`weak` 在本函数里**只有一个写入方向**。`found == true` 时执行 `continue`，
没有任何把它复位为 `false` 的路径。而 `weak` 的初值来自事件创建时的**位移判据**
（`:1868` `= !strong`；OB 同型 `:2131`）——本函数在其后运行，**成为该字段语义的最后写入者**。
后果是：一个**通过了位移门槛的强 CISD**，只要后续 N（默认 5）根内没有同向 FVG，
就被永久打成 `weak = true`，而**"位移不足"与"缺少后续 FVG"两种完全不同的原因塌缩成同一个字段**，
事后无法从 CSV 区分。

**这不是纯观感问题**，`weak` 是渲染与导出的真实输入：

- `:5342` CISD 线色：`g_result.cisd[k].weak ? InpColorCISDWeak : InpColorCISD`
  —— 而 `:5309-5313` 明确写着本指标的既定口径是
  *"CISD 不做 WEAK 分级处理…质量改以**颜色**区分（OK = InpColorCISD，WEAK = InpColorCISDWeak）"*。
  于是颜色这个**唯一**的质量信号被污染。
- `:5498` OB 配色同型；`:1179`/`:1242` CSV 的 weak 列。
- 与 `:3537-3544` 的自我承诺（该层"不参与任何判定"）不符：它确实进了输出。

**触发条件**：`InpCisdFvgLookahead > 0`（默认 5）。只要某次强 CISD 触发后的 5 根内没有同向 FVG ——
在位移造势之后紧接着走反向/震荡的形态里很常见。

**最小修法**（改为双向显式赋值，并让 OB 同步同一结论）：

```mql5
      g_result.cisd[k].weak = !found;
      for(int o = 0; o < g_result.nOB; o++)
         if(g_result.ob[o].bar == b && g_result.ob[o].dir == dir)
         { g_result.ob[o].weak = !found; break; }
      if(found) continue;
      // …（原 OB 循环删除，避免二次写入）
```

> 若产品口径其实是"缺 FVG 就算弱"，那也应**新增独立字段**（如 `fvgOk`）而不是复用 `weak`，
> 否则 CSV 无法回溯"这条为什么是弱的"。

### P1-2 HTF 快路径的"变化判据"漏掉开盘价 —— 新 HTF K 线开出后实体用旧 `open` 画

**位置**：`Indictor/TradFi_Structure.mq5:4715-4723`

```mql5
   double band = (g_curATR > 0.0) ? g_curATR * 0.1 : 0.0;
   bool   moved = (h != g_htfC0H) || (l != g_htfC0L) ||
                  (MathAbs(c - g_htfC0C) >= band);
   if(t1 == g_htfC0T0 && t2 == g_htfC0T1 && !moved) return;

   g_htfC0T0 = t1; g_htfC0T1 = t2;
   g_htfC0O = o; g_htfC0H = h; g_htfC0L = l; g_htfC0C = c;
```

**取证**：`g_htfC0O` 全文件只有两处出现 —— 声明（`:906`）与写入（`:4723`），**从无读取**
（`Select-String g_htfC0O` 仅 2 命中）。即它是一个**死缓存**，而 `open` 恰恰是
`DrawHtfCandleGeom` 决定实体上下沿（`:4603-4604` `bodyHi = MathMax(o,c)` / `bodyLo = MathMin(o,c)`）
与阴阳色（`:4583` `up = (c >= o)`）的入参 —— **"只变了 open"的变化被静默吞掉**。

**为什么右侧模式下会漏**：新 HTF K 线开盘时 `o` 必然跳到新值，而
`t1`/`t2` 在 `HTF_PLACE_RIGHT` 下由 `g_htfSlot` 网格算出（`:4705-4706`），
**不随 HTF 换根变化**；只要此时新 HTF 的 `h`/`l` 恰好等于上一根缓存值、且
`|c − 缓存c| < 0.1×ATR`，整条早退成立 ⇒ 新 HTF 实体仍按**上一根的 open** 绘制，
直到 h/l/c 走出死区或图表换新 bar（`:4975` 强制清零缓存）。

**触发概率**：偏低但真实 —— 需要 `h`/`l` 与上一根**精确相等**（价格连续性下常见于上一根
收在最高/最低价时）。**严重度**：数据错误但自愈快（下一次条件变化即修正），故列为 P1 末位。

**最小修法**：

```mql5
   bool   moved = (o != g_htfC0O) || (h != g_htfC0H) || (l != g_htfC0L) ||
                  (MathAbs(c - g_htfC0C) >= band);
```

### P1-3 `BREAK_BODY` 的抬头口径与实现不符（"实体完全越过" vs 只判近端越位）

**位置**：声明 `:2440`，实现 `:2505-2519`

```mql5
//:2440   · BREAK_BODY （默认）实体**完全越过**结构位 —— 向上 min(open,close) > level |
```
```mql5
      case BREAK_BODY:
         return isUp ? (MathMin(open[i], close[i]) > level)
                     : (MathMax(open[i], close[i]) < level);
```

`MathMin(open,close) > level` **只保证实体靠近该位的那一端**越过去了；
`open < level < close`（实体**跨位**）同样满足它，却被算作"已破"。
而"实体跨位的 K 线不算 sweep"正是用户在 v1.50-s72 亲口裁定的形态（`:399-400`）。
更要注意 `:2444` 声称三档严格度是**全序** `BODY ⊂ CLOSE ⊂ WICK` ——
按当前实现，跨位大实体在 BODY 与 CLOSE 下都被判破位，**全序仍成立**，
故这是**注释口径**问题而非逻辑矛盾；但它会让按文档理解 BODY 的人得出错误结论。

**最小修法**（二选一，必须显式二选一）：

- 只想改口径描述 → 把 `:2440` 改成"实体**近端**越位（`min(open,close) > level`）"；
- 想要字面的"完全越过" → `isUp ? (open[i] > level && close[i] > level) : (open[i] < level && close[i] < level)`，
  注意这会**减少事件**，属会改变结构集合的改动，须单独归档对比。

### P1-4 `DumpEvents` 八路归并的平局裁决是"代码顺序"，且未记录口径

**位置**：`Indictor/TradFi_Structure.mq5:1139-1147`

```mql5
      int pick = -1, bestBar = -1;
      if(i < g_result.nMSS  && g_result.mss[i].bar  > bestBar) { bestBar = g_result.mss[i].bar;  pick = 0; }
      if(j < g_result.nBOS  && g_result.bos[j].bar  > bestBar) { bestBar = g_result.bos[j].bar;  pick = 1; }
      …
      if(ch < g_result.nChoch && g_result.choch[ch].bar > bestBar) { bestBar = g_result.choch[ch].bar; pick = 7; }
```

八路全是**严格 `>`**：`bestBar` 相等（同一根 bar 上两类事件）时比较**不更新** `pick`，
裁决权落在**最后一个 `bar == bestBar` 的判断**上，即
`CHoCH > CLOSURE > OB > FVG > SWEEP > CISD > BOS > MSS` ——
**不是**事件创建序。而同一根 bar 产多类事件是常规情形：
主循环对同一根 `i` 依次调用 `CheckBreakAgainstRefs`(`:3790`) → `CheckCisd`(`:3791`) → `CheckFvg`(`:3797`)，
所以 CSV 里 `CISD` 会排在 `MSS` **之前**，与创建序相反。`:1131-1133` 的注释只声明了"旧→新"，
平局口径**既无处置也无记录** ⇒ 两份归档按行 diff 会产生假阳性。

**最小修法**：把八路 `>` 改成 `>=` 显式化"后判者优先"并写进 CSV 头部；
或在 `StructureEvent` 加自增序号作次级键（更贴合"创建序"）。

## P2 — 边界 / 健壮性缺陷（当前多半不可触发，但契约不完整）

### P2-1 `CisdOriginBar` 的扫描无 `ArraySize` 上界

`:2650-2672` 的 `while(j <= oldestBar)` 内直接 `close[j]`/`open[j]`，唯一上界 `oldestBar`
由调用方传 `analysisStart`（`:3922`/`:3930`），入口只判 `extremeBar < 0`。
全量模式下 `analysisStart = rates_total - 1`（`:3708`），恰好贴住数组末端 ——
当前**不越界**，但任何让 `analysisStart` 超出的路径（如传入更长的候选窗口）都会
`array out of range` 中止 `OnCalculate`。同文件其它扫描点普遍带 `ArraySize` 守卫
（如 `:2219`、`:2624`），此处是唯一缺口。

**修法**：`while(j <= oldestBar && j < ArraySize(close))`。

### P2-2 `CheckFvg` 的"越界守卫"与"宽度门槛"共用一个条件

`:2231` `if(InpFvgMinWidthATR > 0.0 && c3 >= 0 && c3 < ArraySize(atrArr))`。
`atrArr` 只分配 `analysisStart + 1`（`:2372`），而 `c3` 来自 `min(analysisStart, …)`，
故 `c3 < ArraySize(atrArr)` **恒真**、是死条件。危险不在当下，而在**耦合**：
一旦循环起点放宽，该 `if` 整体为假 ⇒ **最小宽度门槛被静默关闭** ——
正是 `:2228-2229` 要挡的 tick 级噪声缺口会被全部记录，且不报错。

**修法**：把越界与门槛解耦（越界取 `0` 并显式告警，而非让门槛一起失效）。

### P2-3 `Upsert*` 三兄弟丢弃 `ObjectCreate` 返回值却仍 `return true`

`:4067-4077`（`UpsertLine`）、`:4122-4133`（`UpsertText`）、`:4170-4181`（`UpsertRect`）：
新建分支不检查 `ObjectCreate`，函数仍返回 `true`（契约是"创建或修改过 ⇒ 需要重绘"）。
创建失败时该名字**每帧**重走新建分支 + 每帧 `changed = true` ⇒ 每帧 `ChartRedraw()`，
而图上永远缺该对象、无任何报错或诊断计数。当前不可复现（需对象数上限/坐标非法等），
但它是全文件唯一的对象创建入口，影响所有渲染调用方。

**修法**：`if(!ObjectCreate(...)) return false;`

### P2-4 `SceneSetAdd` 扩容不校验 `ArrayResize`，且核心不变式从未显式建立

`:3981-3999`。集合正确性建立在 `ArraySize(g_setKey) == g_setMask + 1` 上，但
`ArrayResize` 返回值被丢弃、`ArraySize(g_setKey)` 全文 0 次引用。失败或
`(g_setMask+1)*2` 溢出时不变式被破坏且无检测 ⇒ 探测越界（停算）或 `g_setUsed` 清零
致同名重复插入 ⇒ 仍应保留的对象被回收段误删。

**修法**：`if(ArrayResize(g_setKey, newCap) != newCap) { /* 回退 */ return; }`，
并在 `SceneSetAdd` 入口加一条 `if(ArraySize(g_setKey) != g_setMask + 1) SceneSetRebuild();` 自检。

### P2-5 `OnCalculate` 的"新 bar"判据是跨品种/周期持久的 `static`，且只比 bar 总数

`:5881-5899`：

```mql5
   static int s_lastRates = 0;
   bool firstRun = (s_lastRates == 0);
   bool newBar   = (rates_total != s_lastRates);
```

`static` 跨 `OnDeinit/OnInit` 保留（文件自己在 `:4699-4700` 承认该语义），判据不含
`_Symbol`/`_Period`。换品种/周期后若新图表 `rates_total` **恰等于**旧值，
`newBar == false` ⇒ 命中快路径 ⇒ `ComputeStructure`/`RenderScene`/`DumpEvents` 全部跳过，
新图上短暂残留上一品种的结构（下一根 bar 自愈）。

**修法**：提升为全局并在 `OnInit` 清零，或把 `_Symbol` + `_Period` 纳入判据。
